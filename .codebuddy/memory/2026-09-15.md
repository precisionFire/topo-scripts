## 追加修复：主循环定时器防重复启动（扁棒 + 中棒）
- 用户追问「setInterval 会不会重复」→ 核查确认会：`startSteelSimulator()` 在顶层被调用一次，内部 `setInterval(...,100)` 句柄既不保存也无 clearInterval、无防重复标记 → 脚本被重复加载即两个 timer 永久并存。
- 影响面判断（重要，勿夸大）：
  - 位置推演**不会翻倍**：`updateSteelStates()` 的 dt = `(getServerNow() - steel.updateTime)/1000`（真实时间差，非固定 100ms），两 timer 交替只各推自己那段 dt，钢坯总位移不变；代价是 CPU 翻倍、两 tick 贴近时后一次 dt≈0 白跑。

- 改法（先清旧、再起新，比「直接 return 跳过」稳，因为重复加载时全局 var 状态已被第二份重置，让新循环接管更干净）：
  `if (window.__steelSimulatorTimer) { clearInterval(window.__steelSimulatorTimer); } window.__steelSimulatorTimer = setInterval(() => {...}, 100);`
- 已改文件（lint 0 错误）：扁棒线轧机.js（约 2862~2887）、中棒线轧机.js（约 2724~2749）。
- 同源隐患（本次未改，待确认）：顶层 `const dataCollector = new DataCollector(graphView); dataCollector.start();`（扁棒约 3643 行）内部另有 1 秒 `setInterval` 刷图表；重复加载会 new 出第二个实例、第二个 1 秒定时器（`this.isRunning` 守卫对跨实例无效）。大棒线轧机.js 同为主循环裸 setInterval（约 2752 行），同样未改。

## 排查结论：扁棒"运行状态离线时是否不进入任何判断"
- 结论：**不是**。`updateSteelStates()`（2717~2758）**没有任何全局运行状态门禁**，无条件遍历 `SteelStateStore.data` 全部钢坯执行「状态判定→速度求解→applyCollectionPointControl→位置更新→下线判定」。runningState=0 时推演照跑。
- runningState 的**唯一**使用点是 `isActiveCollectionPoint(tag)`（1785~1802），且只对 `millstate*` 生效：`millstate*` 且 `runningState` 非真 → 该点**不参与**约束；`track-*` 热检 1787 行直接 `return true`，永不看运行状态。
- 该函数被 6 处消费，语义均为「跳过该 millstate 点」而非跳过钢坯：`getNextCollectionPoint`(1812)、`getLastPassedPoint`(1828)、`getTailNextPoint`(1844)、头约束 `clipHeadBySignals`(2083)、尾约束(2133)、(2207)、(2548)。
- 顺带发现：`isActiveCollectionPoint` 内 1794 行 `var rolling = node.a('rolledState')` 声明后从未使用（死变量），与 1781 行注释「需要检查运行状态和轧制状态」不符——实际只看 runningState。
- 另一处"提前返回"与运行状态无关：`applyCollectionPointControl` 对 `steel.state === 'ENTRY'` 直接 return（1969~1972）。

### 补充纠正（用户指出：热检 ≠ 轧机，二者不是同一类对象）
- 热检 `track-*`：只有 `rolledState` / `有钢信号`，**没有** runningState 概念；`isActiveCollectionPoint` 1787 行对非 millstate 恒 `return true`。
- 轧机 `millstate1~23`：有 `runningState` + `rolledState`；后端咬钢信号名 `Stand{N}MaterialEngaged` 经 `BACKEND_POSITION_ALIASES`(225~249) 映射到 `millstate{N}`。
- **轧机有两条被使用的通道，只有第一条受 runningState 门禁**：
  1. 作为集合点的**阻挡/放行判据** → 全部经 `isActiveCollectionPoint`(1785~1802)，runningState 非真即整点跳过（消费点 1812/1828/1844/2083/2133/2207/2548）。
  2. 作为**位置基准/位置证据** → `resolvePositionX`(261~274) 取 `All_POSITION_MAP.get('millstateN')`，**完全不读 runningState**。消费方：`applyProcessConstraints`(1151/1251/1264 推算 calcHeadX/calcTailX)、`applyPositionCorrection`(3078/3093~3096/3114/3149/3158 写 `steel.headX`/`steel.tailX`)。
- 结论修正：**"轧机离线就不进入任何判断"不成立**。离线只摘掉它的阻挡作用，其 X 仍被当作钢坯头/尾的位置证据——`forwardSimulatePosition` 以它为推算起点；「无 time」兼容分支更是直接跳位置（3153 `steel.headX = pos`、3162 `steel.tailX = pos`，仅经 clipHead/TailBySignals 裁剪）。

## net-route-switch 能否支持「蓝牙 + WiFi」双出口（仅代码评估，未改动）
- 用户提问假设场景：蓝牙和 WiFi 各承担一个出口（一内网一外网）。结论：**当前版本不能直接用**。
- 三处障碍（均在 tools/net-route-switch.ps1）：
  1. `:127` 候选网卡过滤写死 `-notmatch 'Bluetooth|Sangfor|VNIC|Loopback'` → 蓝牙 PAN（描述通常 `Bluetooth Device (Personal Area Network)`）根本进不了候选列表。
  2. `:124` 用 `Get-NetAdapter -Physical`；蓝牙 PAN 是虚拟适配器可能不在其中，且 -Physical 不报错 → `:125` 的 catch 兜底不触发，双层漏掉。
  3. 角色写死「WiFi = 内网出口 / 另一个 = 外网出口」（`Get-Adapters` 返回 Wifi/Usb 二元组），蓝牙若在内网侧无法表达。
- 改造方向（若用户确认要做）：配置区拆出 `ExcludeMatch` + `BluetoothMatch`（蓝牙仅作最后候选，不破坏现有 USB 方案）；候选回退全量 `Get-NetAdapter`；新增 `-IntranetIf` / `-InternetIf` 显式指定网卡名或 ifIndex。
- 现实限制（与脚本无关，需向用户说明）：蓝牙共享带宽仅 1~2 Mbps，不适合外网主力；蓝牙 PAN 易掉线，脚本每次现探测 → 掉线报「没找到」重跑即可。
