# 记录链权重策略（2026-10-15 确立）

> **适用范围**：本仓库 `.codebuddy/memory` 下的全部记录文件（MEMORY.md / 日志 / 设计档案 / 分卷子文件）。
> **动机**：单次代码改动越来越小（如 v1.10 只改 `H7`→`H8` 一个字符），记录量反而持续增长；且已实际发生三类事故——
> ① 记录与代码不一致导致误判（档案记 v2.0~v2.3，代码里没有，一度误判"本地仅到 v1.9"）；
> ② 文件头精简后设计档案 100+ 处行号全体失效，必须返工重校准；
> ③ 单文件档案（38 KB）被编辑工具清为 0 字节，靠上下文原文才恢复。
> **目标**：把"记什么 / 记在哪 / 记多少 / 谁来淘汰"变成**可判定、可核对**的动作，而不是靠感觉。

---

## 一、四层载体（与用户初版三级设想的对应）

| 层 | 载体 | 记什么 | 不记什么 | 与初版设想 |
|---|---|---|---|---|
| **L0** | `.js` 文件内注释 | 只解释**这段代码**的局部规则/坑（如 `H8_OFFLINE_HEAD_X` 为何是 1800） | 全貌、历史、待办 | 新增 |
| **L1** | 当日日志 `YYYY-MM-DD.md` | 过程、试错、临时态、小改动、待确认项 | 规则结论、设计复述 | = "无定义性 → 每日工作" |
| **L2a** | 设计档案·**稳定事实** | 架构、规则、常量语义、外部接口、已知残留 | 时间线、流水改动 | = "定义性 + 较大改动 → 设计文档" |
| **L2b** | 设计档案·**版本记录** | **定义性 + 行为/规则/接口变化** | 纯注释、纯样式、行号 | = "→ 版本记录" |
| **L3** | `MEMORY.md` **索引行** + topic 子文件正文 | 产线级/跨产线、协作方式、跨会话必须知道、碰了就踩坑 | 单文件实现细节 | = "极重要 → MEMORY"（修正：MEMORY.md 是索引，正文必须落子文件） |

**总原则：向上引用，不向下复制。** L1 引用 L2 只写"详见设计档案 §X"，不复述内容；L3 索引只写一行指针，正文在子文件。

---

## 二、权重公式（把"很/比较/有点"变成可算）

```
W = 2D + S + P + T

D 定义性   : 是否制定了"以后必须遵守的规则/约定"        0/1
S 作用域   : 单画面 0 · 单产线 1 · 跨产线或影响协作方式 2
P 不可推导 : 代码 / git 里读不出来                      0/1
T 时效     : 长期契约 1 · 一次性过程 0
```

**落点：W ≥ 5 → L3；W 3–4 → L2；W ≤ 2 → L1。** L0 不参与打分，仅由"是否解释局部代码"决定。

代入验证（也是过去噪声的成因）：

| 事项 | D | S | P | T | W | 落点 | 说明 |
|---|---|---|---|---|---|---|---|
| v1.10 H7→H8（分期命名 + 下线规则） | 1 | 1 | 1 | 1 | **5** | L3 | 与事实吻合（MEMORY.md 已有「产线分期命名约定」节） |
| 冷床 / roll-y3 能力（代码有、记录无） | 0 | 1 | 0 | 1 | **2** | L1 先登记 | 长期化后再升 L2 |
| v1.4「仅注释整理」 | 0 | 0 | 1 | 1 | **2** | L1 | 本不该占版本条目 |
| 0 字节事故 → "档案须拆分、弃用行号" | 1 | 2 | 1 | 1 | **6** | L3 | 事故过程 L1，防复发规则 L3 |

## 三、生命周期（进退机制，防止只进不出）

| 动作 | 触发条件 | 做法 |
|---|---|---|
| **晋升** | 同类事件在 L1 出现 ≥2 次，或某条日志开始被当规则引用 | 提炼进 L2/L3；L1 原条目改为"结论已沉淀至 X" |
| **合并** | 同一规则再次被修改 | 就地更新 L2a 原条目；L2b 只加一行"vN：调整 X 规则"，不新开条目 |
| **作废** | 代码回滚 / 被推翻（如 v2.0~v2.3） | 保留因果但加 `⚠️ 已作废，勿引用`，并在该节顶部提示；**不删除**（删掉后人会重踩） |
| **淘汰** | 断言已被代码推翻（如"与 v2.1 三方一致"） | 删除或改写为"事实以代码为准" |
| **归档** | 日志 >30 天 | 结论留档、过程按月归档；MEMORY 只留指针 |

> ⚠️ **与既有规则的协调（优先遵守）**：2026-09-17 用户明确「**记忆文件不得为压缩体量而删改**」——
> MEMORY.md / 日志超限时禁止合并、删除、改写已有条目，减体量只能走「整段原文搬迁到子文件 / 下沉到日志」，且**必须先经用户确认**。
> 因此本策略的 **作废、淘汰、归档、去重** 四类动作，一律**先提议、经用户确认后再执行**；本策略不构成对既有条目的自行删改授权。

---

## 四、冲突裁决（必须写死，否则分层也会自相矛盾）

**权威顺序：代码 > git 历史 > L2b 版本记录 > L2a 设计事实 > L1 日志 > L3 索引。**

两条硬规则：
1. 档案与代码冲突时，**当场以代码为准并修正档案**（"本地仅到 v1.9"式误判的根因就是缺这条）。
2. **禁止写"与 X 三方一致""已同步"这类自证式断言**——无法被验证，且一旦失效会误导。

---

## 五、写入预算与禁止事项

- 单次任务：除首次建档外，**最多写 2 个层级**；L2b 增行 ≤1；L3 索引增行 ≤1；L1 单条 ≤5 行。
- **禁止**：同一事实写两处；在文档里写行号（改用 `function xxx` / 常量名锚点，需要位置时搜索定位）；复制原文段落（只留路径 + §编号）。
- L2b 只写"**变了什么 + 为什么 + 影响面**"，不写"改了哪几行"。
- 代码文件头只保留：产线信息 / 关键约定 / 当前版本摘要 / 运行机制 / 待核对项 / 引用入口；详细版本记录一律在 L2b。

---

## 六、边界例外（权重低但强制升级）

1. **外部 / 现场约定**（口头承诺、第三方接口契约、责任人承诺）：即使 W 低也强制 ≥L2，且必须记"谁定的、何时、依据"。
2. **事故与教训**：过程进 L1，防复发规则强制进 L3。
3. **临时态**：标注"临时，YYYY-MM-DD 失效"，过期即删，不得沉淀进 L2。

---

## 七、执行机制（防漏写 / 漏升级 / 漏淘汰）

每次任务收尾做三问自检，并在回复中**显式声明落点**：

```
本次记录落点：L1 日志 1 条 / L2a §X 更新 / L2b vN / L3 索引行
① 是否产生新规则或新约定？   → L2b +（作用域 ≥ 产线级时）L3
② 是否推翻了旧记录？         → 标记 ⚠️ 已作废 + 修正引用处
③ 是否只是过程？             → 仅 L1，且 ≤5 行
```

显式声明的价值：漏写、该升级未升级、该淘汰未淘汰，用户一眼可核对，避免静默偏差。
